# Mission Pool integration

The Missions screen is built at runtime by `GravityHalfDeadApp.MissionsUI.cs`. It is mounted under
the existing main **MISSIONS** navigation item and contains two top tabs:

- **MISSIONS** is active by default and always renders exactly three mission cards.
- **ACHIEVEMENTS** is intentionally empty for now.

The panel uses the same responsive 1080 x 1920 safe-area composition as the rest of the game. The
Nova portrait, mission-set number, canonical score multiplier, bounded mission title, progress bar,
green completion tick, rewarded-ad removal, and the 5,000 **G Coin** skip control are generated by
Unity UI. Mission titles use best-fit sizing and truncate vertically inside a fixed card column so
they cannot overlap the action controls on narrow phones or tablets.

## Firebase data layout

Realtime Database is authoritative for the pool and each player's active set:

```text
missionPool
  version: 1
  setsPerTier: 3
  maximumTier: 6
  behaviors
    collect_coins_one_run
      enabled: true
      scope: "run"
      titleTemplate: "Collect {target} G Coins in one run"
      targets: [100, 250, 500, 750, 1000]
      lateTargets: [500, 750, 1000]
    ...28 more behavior definitions

players/{uid}
  coins: 25000
  missions
    setNumber: 4
    tier: 2
    completedCount: 7
    active
      0
        instanceId: "32-character-generated-id"
        definitionId: "jump"
        title: "Jump 50 times"
        parameter: ""
        target: 50
        progress: 12
        status: "active"
        tier: 2
        assignedAt: <server timestamp>
      1: ...
      2: ...
    updatedAt: <server timestamp>
```

Firestore remains the compatibility/profile mirror. The mission controller mirrors
`mission_set_number`, `mission_tier`, `active_missions`, `completed_missions`, and
`score_multiplier` into `users/{uid}`. The existing Firestore player listener supplies the stored
multiplier on login (default `x1`); every three genuinely completed missions increases it by one,
capped by the existing game rule at `x30`. Skipped or ad-removed missions resolve a slot but do not
increase the completed-mission count.

## How random retrieval works

1. After Firebase authentication succeeds, Unity reads `/missionPool` once and subscribes to
   `/players/{uid}/missions` in real time.
2. If the player already has three saved mission instances, those exact instances are restored.
   Reopening the app therefore does not reroll active missions.
3. If no saved set exists, Unity filters enabled and currently eligible behaviors, avoids the
   previous set where possible, shuffles the candidates, and chooses three unique behaviors.
4. Tier is derived from the set number. With `setsPerTier: 3`, sets 1–3 use Tier 1 targets, sets
   4–6 use Tier 2, and so on. Past the last configured target, a value is chosen from
   `lateTargets`, allowing the pool to repeat without creating hundreds of hard-coded missions.
5. A Firebase transaction writes the three generated instances together. Transactions prevent two
   signed-in sessions from replacing the same set at the same time.
6. Completed, skipped, and ad-removed slots stay visibly resolved until all three are resolved.
   Then the rightmost card slides out to the right and its replacement slides in from the left;
   the same sequence repeats for the other two cards. The set counter increases once per full set.

The bundled fallback in `GravityHalfDeadApp.Missions.cs` contains the same 29 approved behavior
types. It keeps the UI safe if the pool is temporarily unavailable, but Firebase is used whenever
the seed has been uploaded.

## Upload the pool and rules

The complete approved pool is in `mission-pool.seed.json`. From this Unity project folder run:

```bash
firebase database:set /missionPool mission-pool.seed.json \
  --project gravity-half-dead --confirm
firebase deploy --only database --project gravity-half-dead
```

The first command changes only `/missionPool`; it does not overwrite player data. The included
`database.rules.json` lets authenticated players read the pool, denies client writes to it, and
validates the three saved mission slots under their own UID.

## Gameplay event connection

The following existing flows are connected already:

- `OnTapToPlayPressed` resets incomplete one-run counters.
- `RecordRunStatistics` records run score, run/overall distance, run/overall G Coins, and completed
  runs.
- `RecordPowerupCollected` records one-run/overall pickups and supported specific collectible
  targets (Magnet, Shield, and Coin Booster).
- successful power-up upgrades and booster purchases record upgrade/spend missions.
- successful booster reward ads and mission-removal ads record rewarded-ad progress.

The runner should flush its remaining counters before `RecordRunStatistics`:

```csharp
app.RecordMissionRunTelemetry(
    leftLaneCoins,
    middleLaneCoins,
    rightLaneCoins,
    magnetCoins,
    jumps,
    rolls,
    laneChanges,
    chestsOpened,
    chestsCollected,
    runCoins,
    distanceMeters,
    usedRevive,
    usedPowerup,
    diedWithinFirst60Seconds);

app.RecordRunStatistics(score, runCoins, distanceMeters);
```

Call `RecordMissionReviveByAd()` only after the rewarded revive succeeds, and call
`RecordMissionPowerupUsed(powerupId)` only when a collected power-up is activated, and call
`RecordMissionMegaBoostUsed()` when Mega Boost is actually consumed. For any future behavior, use
`ReportMissionProgress("definition_id", amount, optionalParameter)`. Progress updates use player-root
transactions, so simultaneous coin/mission writes stay consistent and a mission can be completed
only once per instance.

## Skip and rewarded-ad behavior

Skipping runs one transaction against `players/{uid}`: it checks the current mission instance,
checks the live balance, deducts exactly 5,000 G Coins, and marks the slot `skipped`. If any check
fails, no coins are deducted. The button is grey and non-interactive when the player has fewer than
5,000 G Coins.

Mission ad placement IDs start with `mission_remove_`. The Google test-ad provider accepts those
placements in addition to shop boosters. A mission changes to `ad_removed` only after Google's
verified reward callback; closing or failing the ad leaves the mission active.

For release-grade anti-cheat, mission completions and rewarded-ad verification should eventually be
moved to a trusted Cloud Function or game server. The current transactional client implementation
is consistent across sessions, but—as with any client-authoritative mobile game—a modified client
cannot be treated as trusted.
